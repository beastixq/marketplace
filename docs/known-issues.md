## BUG-008 Полный Прогон Останавливается В Gobco При Обработке CGO

Status: reproduced locally, open
Severity: medium
Area: testing/coverage/tooling

В `compose-root-full-20261118` unit-тесты (758 узлов), `go vet`, offline-тесты
и statement coverage (88,1 %) прошли. Затем `go tool gobco -branch

Полный прогон не считается успешным: integration/E2E пропущены после ошибки unit,

Исправление инструмента покрытия требует отдельной итерации; проверку не отключали.
В последующем `jobs-unit-20261118` ошибка не повторилась: unit/offline/vet,
statement coverage 88,1 % и branch coverage (603/710 service, 427/570 repository)
прошли. Код инструмента не менялся; причина прежнего сбоя остаётся неустановленной.

## TD-005 Integration Пропускаются При Отсутствующем DATABASE_URL

Status: confirmed, open
Severity: medium
Area: testing/configuration

`internal/testsupport/postgres.go` возвращает `(nil, nil)` при пустом
`DATABASE_URL`. Репозиторные и сервисные integration-наборы затем вызывают
`t.Skip`, поэтому прямой запуск с тегом `integration` может завершиться успешно,
не проверив PostgreSQL. Проверки в Makefile и контейнерном runner не устраняют
этот дефект непосредственного запуска Go-тестов.

Требуется: явный integration-запуск без `DATABASE_URL` или с пустым значением
завершается ненулевым кодом и понятным сообщением `DATABASE_URL is not set`.
Массовый SKIP не считается корректным результатом. Обычные unit-тесты без тега
`integration` по-прежнему выполняются без БД. Проверяется окружение процесса
тестов: при контейнерном запуске DSN уже передаётся через Compose.

Воспроизведение: `env -u DATABASE_URL go test -count=1 -tags=integration -run '_Integration$' -p=1 ./internal/repository ./internal/service`.
Исправление отложено до разбора техдолгов.

Проверено агентом 2026-11-18: после `docker compose stop api` команда

`artifacts/lab2/goose-cli-1794560290585/port-conflict.txt`.
Выбор `ports: ...:0:5432` пока не даёт полной гарантии запуска на этом rootless
хосте. Устранение конфликта требует отдельного согласования; повторный успешный
запуск не закрывает проблему. Не менять системный диапазон портов и не закрывать
чужие соединения как неявную часть тестов.

## BUG-005 Постоянный Тестовый Стенд Хранит Данные В /tmp

Status: fixed and verified locally in working tree
Severity: high
Area: testing/stand/persistence

При ручном прохождении ЛР2 `make test-stand-up` завершился ошибкой
`Compose resources lack a matching test-stand ownership record; refusing mutation`.
Проверкой Docker подтверждены три остановленных контейнера `marketplace-test-local`
от 2026-10-21 и пустая сеть этого проекта. Их labels соответствуют тестовому стенду.
API монтирует `/tmp/marketplace-test-runtime/stands/local` в `/stand`, PostgreSQL —
подкаталог `postgres` в `/var/lib/postgresql/data`.

На хосте отсутствуют `stand.json`, бинарник, конфиг и каталог PostgreSQL по этим
путям. Причина удаления каталога не установлена; очистка `/tmp` при перезагрузке
или обслуживании системы могла привести к такому состоянию. Защита ownership
корректно отказалась менять ресурсы без записи, но сам постоянный стенд зависит
от временного каталога и не имеет удобного сценария восстановления после его потери.

Исправлено в рабочей копии 2026-11-18: постоянный стенд описан корневым
`docker-compose.yml`, API содержит бинарник, конфиг — `config/docker.yaml`,
PostgreSQL использует именованный том `marketplace_postgres-data`. Запуск через
`docker compose up -d` и подключение тестов больше не требуют `stand.json`
или `TEST_RUNTIME_ROOT`. Старый веб-том `marketplace_db-data` сохранён отдельно.

Агент проверил `docker compose down` без `-v` и последующий `up -d --wait`:
количество пользователей/заказов/товаров и версия миграций сохранились
(`2|0|0|12`). API, integration, E2E и traffic работают без `TEST_RUNTIME_ROOT`.
Временные данные активного изолированного прогона по-прежнему нужны для его
восстановления; эта гарантия не относится к удалению runtime во время прогона.

## TD-003 Контроллер Тестов Связан С Развёртыванием Стенда

Status: open, partially implemented
Severity: medium
Area: testing/stand/orchestration

Текущее исправление: корневой Compose содержит API/БД/Redis, `config/docker.yaml`
и именованный PostgreSQL-том. `test-stand-up` — обычный `docker compose up -d`.
Тестовый Compose добавляет только runner. Порядок CI-этапов передан GitHub
`needs`, подготовка/сбор отчёта вынесены в Composite Actions. Unit-команда
не поднимает БД/API; отдельная integration-команда готовит только PostgreSQL.
Общие тесты используют проект
`marketplace` без `stand.json`; локально код монтируется напрямую, `source.tar`
удалён. Имена/порты общего стенда задаёт Compose; controller задаёт отличия
временных окружений. Миграции остаются Goose CLI. Описание ниже фиксирует причины
и остальные границы долга, а не прежние блокеры запуска общего стенда.

Исходная проблема до текущего исправления:
`scripts/testing/controller.py` объединяет управление прогоном, развёртывание
постоянного стенда, сборку инструментального образа, упаковку исходников,
PostgreSQL snapshot/recovery и историю Allure. Обычный `docker compose up -d`
создаёт проект `marketplace`, а тестовые команды ожидают `marketplace-test-local`
и его `stand.json`. DSN и URL заданы внутри тестового Compose. Поэтому существующий
стенд с корректной схемой нельзя выбрать только параметрами подключения, хотя
сами Go integration-тесты используют `DATABASE_URL` и не требуют HTTP-сервера.

Часть долга исправлена отдельным согласованным изменением: корневой `Dockerfile`
содержит двухэтапную сборку самостоятельного API-образа, а runtime подключает
только конфиг. Внешний бинарник больше не создаётся; версия API и версия runner
хранятся отдельно. Применение к уже работающему общему API выполняется явной
операторской командой. Полный deployment без репозитория ещё не реализован.
Миграции вынесены из тестового контейнера: установленный на хосте Goose CLI
вызывается через `make migrate`, в CI есть отдельный шаг установки CLI.
Тестовый PostgreSQL доступен хосту через опубликованный localhost-порт;
временные окружения получают свободные порты автоматически. Подготовка общего
стенда больше не зависит от runner. Общие имена и порты определяет Compose;
controller переопределяет их только для изолированных запусков.
`Stand.reports` теперь подключает историю до единственного этапа генерации;
полная и очищенная публичная версии остаются отдельными результатами этого этапа.
E2E-cleanup подключается к `cache:6379` напрямую, поэтому одного DSN/URL
недостаточно для запуска на стенде с другим адресом Redis.
Обычные этапы runner пока запускаются отдельными временными контейнерами одного
образа. Предложено в отдельной итерации использовать один контейнер на прогон
и выполнять команды через exec; внешняя аварийная очистка должна сохраняться
при гибели этого контейнера. Эта смена lifecycle ещё не реализована.
Остальные пункты требуют рефакторинга; наличие отдельного API-образа не закрывает TD-003.

Целевая граница ответственности:

| Ответственность | Владелец |
| --- | --- |
| Состав, образы, конфигурация, запуск, логи и обновление постоянного стенда | Самостоятельные deployment-файлы и инструкция для DevOps; Make допустим как обёртка |
| Этапы `unit → integration → e2e`, fail-fast, статусы, вызов восстановления и сохранения результатов | Тонкий controller прогона |
| Получение нужного коммита, доставка рабочей копии, сборка инструментов и приложения | Отдельные механизмы подготовки исходников и образов |
| Docker-операции и владение временным окружением; PostgreSQL backup/restore | Адаптеры окружения и хранилища, вызываемые оркестратором |
| История, преобразование, очистка публичных данных и генерация Allure | Механизм отчётности; история подключается до единственной генерации |
| Arrange, действия, утверждения и адресная очистка фикстур | Компонентные тесты и E2E-фикстуры |

Controller вызывает механизмы через явные границы. Сценарии не зависят от его
служебного состояния. Размер файла сам по себе не требует новых абстракций.
Внешний процесс восстановления сохраняется: finalizers внутри убитого тестового
контейнера не выполняются. `acceptance.py` остаётся отдельной проверкой гарантий
инфраструктуры, а не обязательной частью каждого продуктового прогона.

Критерии закрытия:

- DevOps может развернуть, проверить, обновить и остановить постоянный стенд
  штатными командами без controller и каталога конкретного тестового прогона.
  Документированы конфиг, версия приложения и сохранение данных.
- Тестовый контейнер подключается к уже работающему стенду через явно заданные
  DSN/URL, адрес Redis и настройки сети; значения по умолчанию соответствуют локальному стенду.
  Запуск не требует, чтобы стенд ранее создал controller, и не меняет его lifecycle.
- Изолированный режим отдельно создаёт и удаляет только принадлежащие ему ресурсы;
  integration-подготовка не требует лишних API/Redis, когда они не используются.
- Сохраняются точный commit в CI, локальная рабочая копия, отчёт при ошибке,
  `skipped` для незапущенных этапов и восстановление после прерывания.
- Проверяются три повторных integration-прогона и параллельные прогоны. Отдельно
  проверяется совместная работа на одном стенде: глобальный `ExpireOrders` и
  агрегаты пока не позволяют считать всю integration-suite безопасной для этого.
  Два независимых стека не заменяют такую проверку требования 15.
- Требования 3, 4 и 10 ЛР2 сохраняются для формального CI-прогона: отдельное
  тестовое хранилище, подготовка и восстановление после сбоя. Диагностический
  запуск на общей БД не объявляется полным выполнением этих гарантий; откат
  снимка общей БД поверх параллельных ручных записей недопустим.

Источники: задание `/home/roman/bmstu/7sem/testing/labs/2.pdf`, страницы 1–2;
[разбор текущих границ](test-suite-review.md#stand-orchestration-responsibilities),
[текущие команды и ограничения](testing.md#container-test-stand).
Один управляющий шаг GitHub Actions сам по себе не считается дефектом: задание
требует три последовательных логических этапа, а не три jobs. Разделение имеет
смысл при подтверждённой пользе для эксплуатации, с сохранением стенда и recovery.

## BUG-004 API Возвращает Пустые Отзывы Без Параметров Пагинации

Status: open
Severity: medium
Area: API/reviews/pagination
Found: 2026-10-07

Проверено на тестовом стенде PostgreSQL 16 с миграциями 1–12, код `ec1d828`.
Требуется товар с отзывом, созданным покупателем после доставки заказа.

1. Зарегистрировать покупателя и продавца, создать профиль, товар и адрес.
2. Купить товар, оплатить через mock-bank, отгрузить и доставить заказ.
3. Создать отзыв: `POST /api/v1/reviews` возвращает `201` и ID.
4. Запросить `GET /api/v1/products/<id>/reviews` без query-параметров.

Фактически: `200` с `[]`, хотя отзыв создан. Репозиторий применяет `LIMIT 0`
при нулевом значении `PaginationOpts.Limit`.
Ожидается: существующий отзыв возвращается с принятой пагинацией по умолчанию,
либо API явно сообщает, что параметры обязательны. Сейчас ошибки нет.

E2E ЛР2 использует явные `page=1&limit=20` и проверяет ID, покупателя, товар,
оценку и текст отзыва. Это обход подтверждённого ограничения, не исправление.
Ретест: сравнить запросы с пагинацией и без неё после согласованного исправления.
GitHub Issue не создан; ссылку на него добавлять только после разрешения публикации.

## RISK-001 Обновление Цены Без ChangedBy Зависит От Состояния Соединения

Status: confirmed risk, open
Area: products/price-history
Found: 2026-10-07

На том же PostgreSQL-стенде вызов `ProductService.UpdateProduct` с новой ценой
и `ChangedBy=nil` завершился нарушением NOT NULL поля `product_price_history.changed_by`.
Триггер читает `current_setting('app.current_user', true)`; на новом соединении

поля доменной структуры не выражает это условие. В интеграционных сценариях
передаётся `ChangedBy`, как в текущем HTTP-пути. Контракт и исправление требуют
отдельного решения; бизнес-код и старые миграции при выполнении ЛР2 не менялись.

## BUG-001 Payment TTL Starts From Draft Cart Creation

Status: open
Severity: medium
Area: orders/payments
Found: 2026-05-13

Problem:
`PaymentService` считает дедлайн оплаты как `orders.created_at + payment.ttl`.
При single-seller checkout сервис переиспользует существующую draft cart row,
поэтому pending order наследует `created_at` корзины. Если корзина была создана
давно, окно оплаты может оказаться сильно меньше ожидаемого или уже истекшим.

Expected:
Окно оплаты должно начинаться от момента checkout или от отдельного момента
создания payment window, а не от создания draft cart.

Known Context:
- Multi-seller checkout создает новые pending orders, поэтому там `created_at`
  ближе к моменту checkout.
- Обновлять `created_at` при checkout нежелательно: поле начинает терять смысл
  времени создания записи.

Options:
- Добавить отдельное поле вроде `checked_out_at` или `payment_expires_at`.
- Всегда создавать новую pending order при checkout, даже для одного продавца.
- Обновлять `created_at` при checkout только как временный компромисс.

## BUG-002 Absolute Stock Update Can Override Seller's Stale Intent

Status: open
Severity: medium
Area: products/orders
Found: 2026-05-13

Problem:
Форма продавца редактирует `stock_quantity` как абсолютное значение. Если
продавец открыл форму при `stock_quantity = 100`, решил уменьшить запас до `90`,
а пока форма была открыта заказ/отгрузка изменили остаток до `96`, отправка формы
запишет `90`. Это безопасно с точки зрения row lock и constraint
`reserved_quantity <= stock_quantity`, но может потерять намерение продавца
"уменьшить на 10" и фактически уменьшить только на 6 относительно свежего
состояния.

Expected:
Нужно явно выбрать бизнес-семантику редактирования склада:

- абсолютное "установить stock_quantity в N";
- относительное "увеличить/уменьшить stock_quantity на delta";
- optimistic concurrency: абсолютное значение принимается только если продавец
  редактировал актуальную версию товара.

Known Context:
- `ProductService.UpdateProduct` берет `FOR UPDATE` lock и проверяет, что новое
  значение не ниже `reserved_quantity`.
- `ProductRepo.UpdateProduct` сейчас делает `SET stock_quantity = $value`.
- Технической гонки записи без lock нет; проблема именно в stale form / lost
  intent.

Options:
- Добавить `version` или `updated_at` check в форму и API update.
- Перевести UI склада на delta operation для пополнения/списания.
- Оставить абсолютное значение, но явно показать продавцу предупреждение и
  свежий `reserved_quantity`/available stock.
