# Передача бага от тестировщика разработчику

До очистки сохранить версию кода (SHA и признак незакоммиченного снимка), версию
БД/миграций, тест и упавший шаг, обезличенные исходные данные, запрос/ответ и
связанные серверные логи. Исключить пароли и JWT; PCAP синтетического сценария
передавать только после подтверждённого завершения доступа тестовых аккаунтов.

Указать самодостаточные действия через UI/API, а не просьбу запустить внутренний
хелпер. Каталог `artifacts/lab2/<RUN_ID>/` сохраняет исходный снимок и манифест
фикстуры; новые IDs допустимы при повторении. Не требовать возвращения прежних
IDs и не восстанавливать полный дамп на общем стенде с ручной работой.

## Шаблон GitHub Issue

```text
Название: <компонент и наблюдаемая проблема>

Стенд и версия: <URL, SHA/снимок, существенные версии и настройки>
Предусловия: <роль, собственные данные, состояние заказа>

Шаги:
1. <минимальное действие через UI или конкретный API-запрос>
2. <действие, после которого проблема наблюдается>

Фактически: <HTTP-код, состояние/значение, краткая диагностика>
Ожидается: <результат и ссылка на требование/согласованный контракт>
Доказательства: <ссылка на CI run/artifact, обезличенные запрос/ответ и логи>
Учёт в проекте: <BUG-ID в docs/known-issues.md>
```

Реальный Issue создаётся только по отдельной просьбе. После создания добавить его
URL к соответствующему BUG-ID, обсуждать одно наблюдаемое нарушение, не выдавать
предположение о причине за результат расследования. Если сбой возник в подготовке
контейнера/фикстур, сначала классифицировать его как инфраструктурный, а не как
сломанный checkout. При невозможности повторения уточнить версию, данные и окно
ручных изменений; сохранить исходное доказательство, не закрывать баг автоматически.

## Проверка исправления

Повторить исходные шаги на версии с исправлением, сопоставить ожидаемый и фактический
результат, выполнить близкие негативные/граничные случаи и весь затронутый набор.
Добавить регрессионную проверку на уровне владельца поведения: сервис, SQL или HTTP.
Не ослаблять исходный assert ради зелёного отчёта. В комментарии указать проверенную
версию, результат ретеста и регрессии, ограничения. После закрытия перенести краткую
запись в `docs/bugs-history/`; до исправления хранить её в `docs/known-issues.md`.

На `shared` стенде использовать отдельные аккаунты/товары. При чужой связи с тестовым
товаром очистка намеренно останавливается: согласовать с ручным тестировщиком удаление
его действия, затем повторить адресную очистку. Полный снимок можно возвращать только
в согласованное `exclusive` окно; блокировка автоматических запусков не блокирует UI.

Общий каталог и аналитика временно включают синтетические товары/заказы даже при
разных аккаунтах. Для точных глобальных счётчиков нужно exclusive-окно; shared
режим не обещает неизменность общих агрегатов. Сбой Redis при очистке требует
повторной очистки подтверждённых ключей; не заменять её глобальным FLUSHDB.
После гибели controller восстанавливать только его RUN_ID и только до возобновления
ручных изменений. Не использовать старый dump как способ воспроизведения бага
на стенде, где уже появилась новая ручная работа.
