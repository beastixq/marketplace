### Исследовательский раздел
**Тема:** Исследование влияния индексов и Redis-кэширования на производительность

Воспроизводимый пакет измерений: `scripts/research/` (`run.sh` — основной
прогон, `scaling.sh` — лестница масштабирования). Числа в РПЗ берутся только из
сгенерированных артефактов (`research_results/latest/`).

**Исследование 1 — наличие и тип индексов PostgreSQL:**
- Инструмент: `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`, повторы с отбрасыванием
  прогрева, среднее ± СКО.
- 1.1 Наличие: набор запросов с индексами и без них — seq scan vs index scan,
  включая случай хранимой функции, где индекс не помогает.
- 1.2 Тип (простой vs составной): `orders_by_user` — `(user_id)` против
  `(user_id, created_at desc)`; составной устраняет узел `Sort`.
- 1.3 Тип (B-tree vs GIN/`pg_trgm`): подстрочный поиск `name ILIKE '%x%'` —
  B-tree неприменим (Seq Scan) против GIN (Bitmap Heap Scan).
- 1.4 Масштабирование: время текстового поиска при росте числа товаров
  (лестница ~10k/100k/500k) — кроссовер seq scan и GIN.

**Исследование 2 — Redis-кэширование под нагрузкой:**
- Инструмент: нагрузочный тест (`scripts/research/http_load.go`).
- Нагрузка: GET `/api/v1/products/{id}`, `/api/v1/products`,
  `/api/v1/products/{id}/reviews`, `/api/v1/categories`; сценарии Redis off / warm.
- Метрики: среднее время ответа, P95/P99, доля cache hit/miss (Redis `INFO`),
  относительное число обращений к PostgreSQL (`pg_stat_database`).

### Redis-кэширование для описания в РПЗ

Redis рассматривается как внешний учебный слой производительности. PostgreSQL
остаётся источником истины: все изменения записываются в PostgreSQL, а Redis
ускоряет повторные чтения по схеме Cache-Aside.

В реализации используются читаемые ключи без hash: параметры пагинации,
сортировки и фильтров записываются в каноническую query-string часть ключа.
Например, `products:catalog:limit=12&page=1&sort=asc`. Такой формат проще
обосновать в курсовой работе и проверить вручную через `redis-cli`.

TTL задаётся в конфигурации отдельно для карточек товаров, каталога,
категорий и отзывов. Инвалидация выполняется после успешной фиксации
транзакции PostgreSQL; массовое удаление ключей по префиксу использует `SCAN`,
а не `KEYS`, чтобы не блокировать Redis на большом числе ключей.

Для изменения остатков товара используется отдельное правило: кэш карточки
товара `products:{id}` инвалидируется сразу, а кэш каталога остаётся до TTL.
Это осознанный компромисс: каталог может показывать количество с небольшой
задержкой, зато повторные покупки не уничтожают весь catalog-кэш. Точная
проверка доступного количества выполняется в PostgreSQL при добавлении товара в
корзину и оформлении заказа.

Redis также используется для списка отозванных JWT. Для этого слоя выбран режим
fail-closed: если Redis недоступен при проверке токена, защищённый запрос
отклоняется, чтобы не принять уже отозванный токен.
