# Проверочный сценарий ЛР2

Источники: `/home/roman/bmstu/7sem/testing/labs/2.pdf` целиком и примечания
`1.pdf`; реализация и текущие ограничения — [testing.md](testing.md),
известные проблемы — [known-issues.md](known-issues.md).

Это сценарий будущей ручной проверки, а не отчёт о её прохождении. Пользователь
выполняет команды, агент объясняет результат и даёт следующий связанный блок.
Все исходные проверки пользователя сохранены, включая пять одновременных
разработчиков на одном общем стенде и различение их аккаунтов в логах.

## Как ведём проверку

- Для каждого блока сохраняем команду, версию кода/конфига, фактический результат
  и путь к доказательствам в `artifacts/lab2/`. Ожидаемый отказ зависимости
  отличаем от дефекта продукта, ошибки подготовки и ошибки cleanup.
- Большой рефакторинг откладываем до завершения обхода. Неудобства и дефекты
  фиксируем по фактам. Если проверка блокируется, обозначаем блокер и обход;
  обход не объявляем проверкой исходного интерфейса или выполнением требования.
- Общий стенд работает постоянно. Тесты не должны незаметно создавать другой
  стенд, перезапускать сервер или восстанавливать общую БД поверх ручных изменений.
  Аварии с полным восстановлением демонстрируем на собственном окружении.
- До изменения состояния выясняем, какие данные нужно сохранить. Не удаляем
  volume, не откатываем миграции и не запускаем глобальные операции над чужими
  заказами ради получения зелёного результата.
- Новые ручные сущности называем кратко по роли и номеру; комментарии оставляем
  пустыми. Соответствие разработчик → аккаунты/IDs сохраняем в отчёте.
- Исторический зелёный CI не доказывает текущие незакоммиченные изменения.

## 0. Установить исходное состояние

- Зафиксировать ветку, SHA и наличие изменений рабочей копии; отличать версию
  исходников от фактической версии запущенного сервера.
- Проверить контейнеры, процессы, порты, адреса API/БД/Redis, конфиг и место данных.
  Объяснить разницу между `localhost` хоста и контейнера.
- Сверить миграции в коде и в БД, владельцев/права и нужные таблицы. Выяснить
  происхождение несовпадающей схемы; не сбрасывать её автоматически.
- Проверить наличие ручных данных и заказов, особенно `pending`. Учитывать, что
  текущий глобальный `ExpireOrders` может затронуть чужие заказы, а агрегаты —
  параллельные записи. Сохранить необходимые данные до изменяющих проверок.

## 3. Integration на работающем стенде и отказ PostgreSQL

1. Запустить репозиторные и сервисные integration на выбранной существующей БД.
   Подтвердить DSN/экземпляр, реальные SQL и транзакции; не считать массовый SKIP
   прохождением. Записать число выполненных сценариев и cleanup.
2. Не меняя окружение и данные вручную, повторить запуск: результат должен
   совпасть. Сервер не должен перезапускаться или отключаться тестовой командой.
3. Выключить только выбранный PostgreSQL. Запустить те же integration и получить
   ненулевой результат с понятной причиной подключения к БД. Проверить, что тесты
   не подняли её автоматически и не подменили другой БД.
4. Явно включить ту же БД, дождаться готовности и выполнить ту же команду ещё раз.
   Получить успех и сравнить с первыми двумя успешными прогонами — Т14.
5. Проверить удаление собственных фикстур и сохранность контрольных ручных данных.
   На общей БД рост последовательностей сам по себе не означает ошибку cleanup.
   Полное восстановление последовательностей проверяется отдельно в блоке 8.

Для объяснения открыть по одному реальному тесту сервиса и репозитория:
сервис → настоящий repository → PostgreSQL; HTTP-сервер в этот вызов не входит.
Показать commit/rollback, откат частичного резервирования и конкуренцию покупателей
за последнюю единицу. Проверка конкуренции остатков — не замена Т15.

## 4. Redis: использование и отказ

- Сначала подтвердить фактическое использование: конфиг, wiring, чтение своего
  товара и собственный ключ `products:<id>`/TTL. Не требовать реализации кеша,
  если соответствующая функциональность отсутствует.
- Если Redis используется, выключить именно Redis стенда и повторить integration.
  Текущие PostgreSQL integration обходят кеш: ожидается сохранение их результата,
  а не обязательное падение из-за Redis.
- На уже работающем API повторить чтение своего товара: проверить ответ, лог
  отказа Redis и fallback в PostgreSQL. Учесть время повторных подключений.
- Отдельно отличать отказ Redis во время работы от запуска API без Redis:
  текущий startup при `redis.enabled=true` требует успешного Redis PING.
- Если проверяем E2E без Redis, различать падение покупки и падение адресной
  очистки кеша. После включения Redis завершить cleanup своего прогона.
- Включить Redis, подтвердить восстановление и не оставлять зависимость отключённой.
  Новые ключи, session storage и кеширование ради демонстрации не добавлять.

## 7. Требование 12: сессии и токены

- Показать в `cmd/api` и auth-сервисе, что активного серверного session storage
  сейчас нет, а Redis используется для товаров. Очистка списка сессий неприменима.
- Показать `verify_deleted_tokens`: после удаления своих аккаунтов те же JWT
  получают HTTP 401. Проверить это после успеха и аварийной очистки.
- Объяснить ограничение: это не постоянный blacklist JWT. Восстановление снимка
  с повторным использованием user ID не даёт обещания вечного отзыва старого JWT.
  Из этого не следует необходимость добавлять новую session-функциональность.

## 8. Падения этапов и восстановление после прерывания

Сбои с записью данных и полным восстановлением проводить на собственном тестовом
окружении, сохраняя общий стенд для ручной работы. Каждый опыт начинается и
заканчивается проверкой готовности; ожидаемое падение не выдаётся за успех тестов.

| Опыт | Что должно быть видно |
| --- | --- |
| Ошибка unit | unit упал; integration/e2e не запускались и отмечены skipped; отчёт создан |
| Ошибка integration | unit прошёл, integration упал; e2e skipped; отчёт и результат recovery сохранены |
| Ошибка E2E | unit/integration прошли, E2E упал; отчёт и cleanup/recovery выполнены |
| Убийство integration-контейнера после записи | Этап прерван, e2e skipped; зафиксированные данные восстановлены |
| Убийство E2E-контейнера после checkout | Этап прерван; созданные данные очищены/восстановлены по выбранному режиму |
| Убийство controller | Автоматическое завершение не обещается; явный restore по RUN_ID завершает восстановление и убирает свой orphan runner |
| Ошибка восстановления | Общий результат неуспешен; сохранены диагностика и необходимые ресурсы, следующий прогон не маскирует незавершённое восстановление |

- Показать снимок до изменяющих этапов, состояние после аварии и после restore.
  Проверить данные, последовательности, Goose-версии, владельцев и права.
- Проверить повторный restore: после успешного восстановления он не должен
  повторно затирать последующие изменения. Затем выполнить успешный прогон.
- Для shared E2E показать адресную аварийную очистку при сохранении ручных данных
  и работающего API. Она не является полным восстановлением общей БД.
- Объяснить роль внешнего процесса: finalizers убитого контейнера не выполняются.
  Разделять assertion failure, setup failure, interruption и cleanup failure.
- Отключение ноутбука не считать гарантией немедленного автоматического восстановления.

## 9. Пять разработчиков одновременно на одном общем стенде — Т15

- Запустить пять E2E одновременно против одного API и одной БД, без пяти скрытых
  стендов. Подтвердить перекрытие времени выполнения и отдельные результаты.
- Каждый прогон создаёт собственные аккаунты и товары; после завершения своих
  данных не остаётся, чужие фикстуры и контрольная ручная запись сохранены.
- Эмулировать также ручные действия без RUN_ID: пять отдельных аккаунтов и
  независимых авторизованных сессий. Не использовать один общий логин.
- Сохранить таблицу разработчик → login/аккаунты → user_id → запрос/время.
  В общем серверном логе выделить действия каждого из пяти по `user_id` и `role`.
  Поле называется `role`, не `user_role`; у пяти покупателей роль может совпадать,
  а IDs должны различаться. Для заказа отличать buyer user ID от seller profile ID.
- Показать метод, путь, статус и время, сопоставить с UI/API-действием. Разные IP
  и RUN_ID для идентификации аккаунта не обязательны. Анонимный запрос и общий
  аккаунт не позволяют достоверно определить физического человека.
- При необходимости сопоставить собственные HTTP-потоки PCAP с аккаунтами и
  серверными логами; порт/IP сам по себе не доказывает личность разработчика.
- Отдельно оценить параллельные integration на одной БД. Глобальный ExpireOrders
  и before/after-агрегаты сейчас не дают гарантии отсутствия взаимного влияния.
  Не выдавать пять успешных E2E за безопасность всей integration-suite.
- Дополнительно показать два параллельных изолированных полных прогона:
  разные Docker-ресурсы/порты/отчёты и отсутствие изменений общего стенда.
  Этот опыт дополняет, но не заменяет работу пяти разработчиков на общем стенде.

## 10. Отчёты и история

- Для отдельного integration/E2E-прогона с HTML использовать
  `make test-integration-report` или `make test-e2e-report`; у изолированных
  команд суффикс тоже последний: `test-e2e-isolated-report`. Обычные команды
  сохраняют исходные результаты и логи без генерации HTML. Полный `test-all`
  и облачный `test-all-isolated` по-прежнему создают отчёты.
- Открыть локальный Allure через HTTP. Показать Unit, Integration, E2E и результаты
  инфраструктуры отдельно, корректный учёт вложенных Go-сценариев без дублей.
- Показать минимум два фактических прогона с историей; RUN_ID и динамические IDs
  не должны создавать новые идентичности одних и тех же тестов.
- Показать успешный, упавший, пропущенный и прерванный этапы; исходные Go
  JSONL/JUnit, pytest Allure, server.log и environment, а не только зелёный итог.
- Объяснить, что JUnit Go не содержит внутренних бизнес-шагов, тогда как pytest
  имеет явные Allure steps. Никаких выдуманных шагов адаптер не добавляет.
- Сравнить полный диагностический отчёт с очищенным публичным: на Pages нет
  паролей, токенов, исходных HTTP-вложений и PCAP.

- Показать артефакты с покрытием ЛР1, итоговый статус тестов и восстановления,

- Открыть публичный URL Allure, объяснить различие test job и publish-report job.

## 12. Передача бага и завершение

- Для найденной проблемы записать версию, конфиг/миграции, минимальные шаги,
  ожидаемый и фактический результат, тест/упавший шаг, запрос/ответ и связанные

  технический долг и неприменимое требование. Issues без отдельной просьбы не создавать.
- Объяснить цикл после исправления: исходное воспроизведение → ретест → регрессия.
- Вернуть PostgreSQL/Redis в рабочее состояние, проверить UI/API, собственную
  очистку и сохранность ручных данных. Составить список проверенного и оставшегося.
